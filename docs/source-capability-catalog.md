# Source and capability catalog

_Last reviewed: 2026-08-18_

HeyNYC reads public-service data from the organization responsible for each source, adapts the result for the current question, and keeps the source attached. It does not turn these records into a new master database, as explained in the [public architecture FAQ](../README.md#is-heynyc-building-another-master-database-of-services). A source can establish only the fields it publishes. `Fetched now` does not mean `verified current now`, and an administrative status does not prove that a resident's underlying problem is resolved.

This table covers every capability registered in the assistant, including the World Cup subtopic, and a [drift test](../tests/test_source_capability_catalog.py) checks that exact set. It catalogs the primary runtime source lanes, not every page that bounded web search might retrieve for a particular question. Messaging and model processors are cataloged separately in the [Privacy Notice](legal/HEYNYC-PRIVACY.md).

## The shared shape

HeyNYC uses composition instead of one location-shaped record for everything:

- Common primitives are `Place`, `Organization`, `Contact`, `Schedule`, and `SourceRef`.
- Human-service records use `Service` and `ServiceAtLocation`, following the [Open Referral Human Services Data Specification](https://docs.openreferral.org/en/latest/hsds/overview.html).
- Events use an `Event` linked to a place when one exists, following the [Schema.org Event](https://schema.org/Event) and [Place](https://schema.org/Place) relationship.
- Civic cases use source-scoped service-request, complaint, violation, inspection, and litigation records, with [Open311 GeoReport v2](https://wiki.open311.org/GeoReport_v2/) as the reference for service-request vocabulary.
- Transit keeps the operator's trip and status records rather than forcing them into a service-location model; scheduled and real-time transit semantics follow [GTFS](https://gtfs.org/documentation/overview/).

Every adapted record should retain the responsible publisher, a source-scoped identifier, a direct source URL, retrieval time, source-provided validity or update time, exact source snapshot or hash where the citation contract requires it, and explicit limitations. Request-specific values such as distance, `scheduled open`, and next opening time are derived facts, not source fields.

This is an interchange contract for one request. It does not require a persistent place registry, foreign keys across agency systems, or cross-source entity resolution. Those would be separate products and should be added only after a resident workflow proves they are needed.
